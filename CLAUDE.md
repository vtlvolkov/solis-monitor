# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Docker Compose stack that monitors a Solis S6-EH1P hybrid inverter over Modbus TCP: `poller` (Python) → `influxdb` (2.7) → `web` (FastAPI + Preact dashboard). Deployed on an Umbrel box; README.md is the user-facing guide (with screenshots in `docs/img/`) and `docs/` holds the detailed guides. The dashboard's Settings page can change three battery settings through the poller (off unless `CONTROL_ENABLED=true` and `WEB_BASIC_AUTH` are set).

## Commands

Python is linted with ruff (`poller/ruff.toml` and `web/backend/ruff.toml`, identical: pyflakes, import order, bugbear, pyupgrade, simplifications; no line-length rule; tests may use semicolons and lambdas). It runs in CI (`lint` job), in both Dockerfiles' test stages (so a lint error fails `docker compose build`), and locally with `uvx ruff check poller web/backend` (plus `uvx ruff check deploy --config poller/ruff.toml`); `--fix` applies the safe fixes. Everything else runs through Docker Compose (requires a filled-in `.env`, see `.env.example`):

```bash
docker compose up -d --build           # full stack
docker compose up -d --build poller    # after editing poller/poller.py
docker compose up -d --build web       # after editing web/
docker compose logs -f poller
```

Tests (they also run inside both Dockerfiles' test stages, after ruff, so a failing test fails `docker compose build`, and in `.github/workflows/test.yml`):

```bash
cd poller && uv run --no-project --python 3.12 --with-requirements requirements-dev.txt pytest          # control + device decoding
cd web/backend && uv run --no-project --python 3.12 --with-requirements requirements-dev.txt pytest   # add -k <name> for one
cd web/frontend && npm test                                                                           # vitest; npx vitest run -t "<name>" for one
cd web/frontend && npm run build                                                                      # tsc type-check + vite build
```

## Architecture

- **`poller/poller.py`**: the only Modbus client. The inverter/logger may accept only one connection, so never add a second client (the web app must read InfluxDB only) and never run two copies of the stack. `REGISTERS` maps field → (input register, type, scale); `build_blocks()` groups them into contiguous FC04 reads; `read_snapshot()` decodes and adds derived fields. `UNIT_KW` handles pymodbus renaming the unit kwarg (`slave` → `device_id`).
- **Modbus pacing**: `Inverter.session()` serialises every request and spaces them ≥ 350 ms apart; blocks are ≤ 50 registers (Solis protocol limits). Ignoring this caused transaction-ID mismatch errors.
- **`poller/control.py`**: the write path. `Controller._plan()` validates a named setting against the inverter's current related values (e.g. SOC bounds from 43010/43018) and returns what to write; `_apply()` enforces the safety model (enabled flag, `MAX_*_CURRENT_A`, one change at a time, rate limit, read-back at 3 s (up to 9 s), audit to `solis_control`). Settings: 43110 bits 1/4/5, 43117/43118 (FC06), 43010, 43011, 43018, 43024, Time-of-Use slots 43707–43791, clock 43000–43005 (all FC16). `poller/api.py` is the transport: a stdlib HTTP server on `:8780` (Docker network only, `Authorization: Bearer <CONTROL_TOKEN>`, falling back to `INFLUX_TOKEN` on installs from before `CONTROL_TOKEN` existed; `GET /health` is the only route without the token: the container healthcheck, liveness of the poll loop via `PollStatus.beat()`/`health()`, never inverter reachability, so an unplugged logger cannot fail an update). `api.py` only parses requests and formats answers; every rule stays in `Controller`. Never add raw register writes, off-grid/feed-in switching, or registers not checked against a live probe.
- **`poller/rawread.py`** (Settings → Debug tab): `POST /debug/read` on the same internal API reads registers by hand, FC03/FC04 only, count ≤ 50, through `Inverter.raw_read()` (same paced session, so still one connection) and returns the request/answer PDUs as hex plus the registers or the Modbus exception. Proxied as `POST /api/settings/debug/read` (`WEB_BASIC_AUTH` + same-origin, not `CONTROL_ENABLED`); `components/DebugCard.tsx`, `lib/debug.ts`. It is deliberately read-only: never add a write function to it (writes belong to `control.py` and its safety model).
- **`poller/notify.py`**: Telegram alerts (`Alerts` turns tracker events, outage SOC levels, poll failures and an inverter clock off by `ALERT_CLOCK_DRIFT_MIN` (from the device cache's clock vs `read_at`, `device.clock_drift_s`, three reads in a row) into messages; `Telegram` sends them from a background queue with retries). The poll loop keeps inverter-read errors (alerts) separate from InfluxDB write errors (logged only).
- **`poller/mqtt.py`** (Settings → System → MQTT · Home Assistant): publishing only, it never subscribes, so nothing on MQTT reaches the inverter (keep it that way). `MqttStore` (`/data/mqtt.json`, mode 0600, wins over `MQTT_*`; the password is never returned, `public()`/`password_set`), `validate()` (its messages are listed in the frontend's `lib/mqtt.ts` `SERVER_TEXTS`), `build_state()` (`<prefix>/state`, retained, every `interval_s` and at once on an event), `event_message()` (`<prefix>/event`, QoS 1), `discovery()` (Home Assistant configs: one device `node_id(prefix)`, `SENSORS`/`BINARY`; serial from the device cache, re-sent when it appears; an empty retained config removes an entity), `MqttPublisher` (paho-mqtt in its own thread: connect, then paho's loop reconnects; will `<prefix>/status` offline; `reconfigure()` restarts it; `test()` with its own client id). The poll loop calls `publish_event`/`publish_state` after Telegram, inside a try, so a broker can never stop a poll. Internal API `GET/POST /mqtt`, `POST /mqtt/test`, proxied by `web/backend/app/routes/mqtt.py` as `/api/settings/mqtt*` (`WEB_BASIC_AUTH` + same-origin, only the known keys, the password never logged; `components/MqttCard.tsx`). Checked against a real Mosquitto and Home Assistant 2026.11 (25 entities, no warnings); user guide `docs/mqtt.md`.
- **`poller/outages.py`** (planned outage schedule, графік відключень): `Yasno` wraps the undocumented JSON of app.yasno.ua (`regions/{region}/dsos/{dso}/planned-outages`; the address lookup `addresses/v2/streets|houses|group`; checked live 2026-11-13; slots are minutes from local midnight, `Definite` = outage, `NotPlanned` dropped, anything else shown as possible). DTEK's regional sites block servers (Incapsula), so `SOURCES` of `kind: "mirror"` (Kyiv Oblast, Dnipro, Odesa) read the community mirror Baskerville42/outage-data-ua from raw.githubusercontent.com (`Mirror`, `parse_mirror`: `fact.data[<unix local midnight>]['GPV3.1'][hour 1..24]` = yes/no/first/second/maybe/mfirst/msecond, half hours kept; `warning` when its `lastUpdated` is over 3 h old); they pick the group from `GET /outages/groups` (no address lookup; the card links to DTEK's own search). `OutageStore` keeps only source, group and Telegram choices (`/data/outages.json`, never the address) and the last good schedule (`/data/outage-schedule.json`). `OutageWatcher` fetches every 15 min while configured, announces published/changed days, sends "30 min before" and "battery will not last" once per outage, and builds the payload with `verdict()` (minute by minute from the SOC expected at the start, above the backup floor, at the usual load per local hour from `load_profile_flux`, 14 days). Internal API: `GET /outages`, `GET/POST /outages/config`, `GET /outages/groups|streets|houses|group?…` (the query string is parsed in `api.do_GET`); proxied by `web/backend/app/routes/outages.py` as `/api/outage-schedule` (open, the Overview card `components/OutageCard.tsx`) and `/api/settings/outage-schedule*` (`WEB_BASIC_AUTH` + same-origin for the POST; `components/OutageSourceCard.tsx`, `lib/outages.ts`). The browser never talks to Yasno or the mirror.
- **`poller/faults.py`**: fault/status/BMS bit tables (Solis protocol Appendix 2/5/6) and `EventTracker`, which turns each poll into debounced start/end events (grid outage, alarms) written to measurement `solis_event`. Its active events are kept in `/data/events.json` (`EVENTS_FILE`, the `poller-data` volume), so a restart mid-outage neither repeats the start nor leaves the outage open forever: the next polls end it (at restart time, the best guess) or carry on; `Alerts.restore()` takes them over quietly so the "power is back" message keeps the real start.
- **`poller/device.py`**: device details for the Devices tab (`GET /device` on the same internal API; a background thread refreshes it every 60 s because a full read takes ~10 s): serial (33004–33011, ASCII), firmware, clock (33022–27), status (33095), faults (33116–20), BMS (33141–46; battery temperature 33044, S16 ×0.01 °C, found with the Debug tab and not compared with the battery's own display; the documented 33043 (S16 ×0.1 °C, from the BMS) reads 0 on this unit and 33044 is not documented as a temperature; batteries in parallel: `estimated_packs`, 33144 ÷ 1000 for Dyness only, an estimate because no register holds the count, never used for capacity), meter (33251–86). Mappings were verified against a live dump that is kept as the fixture in `tests/test_device.py`. Add a register only after checking it against live values the same way. Battery capacity for the runtime estimate: `CapacityStore` (saved from the Settings page to `/data/battery-capacity.json` in the `poller-data` volume) > `BATTERY_CAPACITY_KWH` > rated Ah (43019) × 51.2 V; `GET/POST /battery-capacity` on the internal API (proxied as `/api/settings/battery-capacity`, `WEB_BASIC_AUTH` + same-origin, not `CONTROL_ENABLED`, never written to the inverter; `components/CapacityCard.tsx`, `lib/capacity.ts`).
- **Logger address** (`poller/address.py`, `poller/scan.py`): `AddressStore` keeps the address saved from the Settings page in `/data/inverter.json` (the `poller-data` volume), which wins over `INVERTER_HOST`/`INVERTER_PORT`/`MODBUS_UNIT`; `Inverter.reconfigure()` follows a change without a restart, and the poll loop simply waits (no alert) while no address is set. Internal API: `GET/POST /inverter`, `POST /inverter/scan` (a /24 of a private network; the poller's own connection is closed during the scan; one scan at a time), proxied as `/api/settings/inverter*` (`WEB_BASIC_AUTH` + same-origin, not `CONTROL_ENABLED`; `components/InverterCard.tsx`, `lib/inverter.ts`). The scan network is only ever suggested by the web app (the configured logger's, or `X-Forwarded-For`); never from the proxy's own address.
- **InfluxDB**: two buckets. The raw one (`INFLUX_BUCKET`): measurement `solis`, tag `host`, one point per poll. The aggregate one (`INFLUX_BUCKET_1M`, default `<bucket>_1m`): 1-minute `mean` (measurement `solis`), `min` (`solis_min`) and `max` (`solis_max`) of every field, written by an InfluxDB **task** `solis-1m` that `poller/downsample.py` creates or updates at every poller start (idempotent; it also backfills the history from before the task, a day at a time newest first, and re-aggregates the last 24 h every 6 h to repair gaps; `prune()` once a day deletes measurement `solis` only — the days come from `RetentionStore` (Settings → System → Stored history, `/data/retention.json`, `GET/POST /retention` on the internal API, proxied as `/api/settings/retention`, `WEB_BASIC_AUTH` + same-origin, not `CONTROL_ENABLED`; the web asks the poller once a minute via `Context.raw_retention()`, env as fallback) over `RAW_RETENTION_DAYS` — never `solis_event`/`solis_control` — older than `RAW_RETENTION_DAYS` (default 90, min 35, 0 = off; `parse_retention` here and `config._retention` in the web read it the same way), each UTC day re-aggregated just before its delete; the aggregate bucket has no retention). The web reads the aggregates for spans ≥ 12 h with windows ≥ 1 min (`influx.use_downsampled`; `window_max` uses `solis_max`), checks every 5 min that the task wrote recently (`downsampled_ready`, any failure → raw) and otherwise reads raw; grid quality always reads raw, so it and the 10 s export refuse days older than the kept raw readings (`grid.raw_from`, sent as `raw_from` for the day picker's `min`; `/api/site` gives `raw_retention_days` to the export dialog); `first_time()` takes the older of both buckets. The dashboard's read-only token must cover every bucket (`secure-tokens` uses `--read-buckets` and replaces an older one-bucket token). Fields:
  - `grid_power = -meter_power` → + import, − export
  - `battery_power_signed` → + charging, − discharging (sign from `battery_direction`: 0 = charging)
  - `total_load_power = house_load_power + backup_load_power`
- **`web/backend/app`** (FastAPI, also serves the built frontend from `static/`): `main.create_app` only wires things: a `Context` (`context.py`: settings, repo, poller client, `LoginStore`, `TariffStore`, the cost caches, `call()`/`poller()` for off-loop I/O, `refuse_write()`/`json_body()` for every POST) is handed to `routes/data.py` (read-only, returns the route functions the MCP server reuses), `routes/settings.py` (every change, `valid_setting`) and `routes/updates.py` (release check and update request, returns the background `periodic_check`) `routes/grid.py` (Grid quality page, `GET /api/grid/quality?range=|date=&v_min=…`, the query builders take an explicit `(start, stop)`: four Flux shapes in `influx.py` — `histogram_flux` (Flux `histogram()`+`difference()`, `le` is the bin's upper edge), `hourly_flux`, `hourly_outside_flux`, `hourly_excursions_flux` (a 0/1 flag differenced, +1 steps counted) — all with `_valid()` dropping readings below 100 V / 40 Hz (an outage is not grid quality); `shape()` groups the hourly rows by the site's local hour and day and is pure for tests; limits from the page within `LIMIT_BOUNDS`; 5-minute cache per period and limits; verified against a live InfluxDB 2.7), `routes/export.py` (CSV downloads: `/api/export.csv` readings over a range or local days at 10s/1m/15m/1h, or one row per local day at `1d` — energy counters by what they added that day, the rest by the mean of hourly means; `/api/export/events.csv`, `/api/export/cost.csv` via `api["cost_history"]`; `sep=;` writes the decimal comma; streamed, row caps in `parse_resolution`), and `routes/backups.py` (the Backup tab: `backups.BackupBridge` shares the control folder with the host like `updates.Bridge`, lists `BACKUP_DIR` (`./backups`, read-only) by the strict archive-name pattern only, and serves downloads behind the Settings login because an archive holds `.env`); add a route to the module whose concern it is, never to `main.py`. `influx.py` is the only module that queries InfluxDB (tests replace it with a fake repo via `create_app(repo=...)`). `validation.py` whitelists every query parameter. InfluxDB OSS has no Flux parameter binding, so Flux strings are built only from those canonical values. `WEB_AUTH_SETTINGS_ONLY=true` limits Basic auth to `/api/settings*` (the Settings page's first fetch triggers the browser prompt; it shows a "Sign in" button on 401). `mcp_server.py` is a read-only MCP server at `/mcp` (own `MCP_TOKEN`, bypasses Basic auth; never add write tools; it reuses the route functions via `DataApi`). `control.py` is the client for the poller's internal API (`/api/settings`, `/api/devices` proxy to it); `POST /api/settings` requires `WEB_BASIC_AUTH` to be set, a JSON body, and same-origin (Origin / Sec-Fetch-Site) to block cross-site requests. `tariff.py` keeps the electricity tariff as versions with a start time (`TariffStore`: `.env` is the first version, saved changes go to `/data/tariff.json` in the `web-data` volume; `GET/POST /api/settings/tariff`, behind the same auth and same-origin checks as other changes, start at the next quarter-hour or a later date and never rewrite the past); `shaping.import_costs` prices each 15-minute window with the tariff in force at that time, so past costs never change. `GET /api/cost` returns today/month blocks (kWh and cost per zone) plus `now` (`shaping.rate_now`: the active zone, its price and when it ends), which is computed per request outside the 5-minute cache. `GET /api/cost/history?month=YYYY-MM` returns per-day grid import split into day/night zones with cost (`shaping.cost_days`; `repo.window_max` takes an optional `stop`, `repo.first_time()` gives the oldest reading) for the cost history page (`pages/CostHistory.tsx`, `charts/CostBars.tsx`, `lib/cost.ts`; URL `?view=cost&month=…&day=…`). `/api/day/history|energy|events?date=YYYY-MM-DD` and `/api/events/calendar?month=` serve the exact-day view of the Charts and Events tabs (`components/DayPicker.tsx`, `DayStats.tsx`, `DayTimeline.tsx`, `lib/day.ts`; URL `?day=`); they are separate routes because `mcp_server.py` calls the `/api/history` and `/api/events` route functions directly. `shaping.py` holds the pure logic: the online flag (45 s), gap insertion, and daily kWh (`counter_increments`: what each 15-minute window maximum of a `*_today` counter added since the window before, summed per local day in Python; the inverter resets the counters at its own midnight, so a reset is detected by the counter falling, never assumed at our midnight, and queries start `BASELINE` (1 h) before the first day; `import_costs` uses the same increments).
- **Dashboard login** (`web/backend/app/auth.py`): `LoginStore` checks the Basic header; the password from `WEB_BASIC_AUTH` is the original, and one changed on Settings → System is kept as a salted scrypt hash in `/data/auth.json` (the `web-data` volume), winning until reset. Changing needs the current password, an existing login (never lets an open dashboard get one), same-origin JSON, and is rate-limited (wrong answers are 400, not 401, so the browser does not prompt). The file is re-read by mtime, so `solis-monitor reset-login` (removes it) takes effect on a running server. MCP has its own token and is unaffected. Umbrel's displayed password becomes stale after a change; the card says so (`UPDATES_MANAGED_BY` names the platform).
- **`web/frontend`** (Vite + Preact + uPlot): flow-direction and dead-band rules live in `src/lib/flow.ts` (each SVG path is drawn a→b; `reversed` = b→a). Colours come only from `src/lib/tokens.ts`, which is published as `--c-*` CSS vars. Live data: `src/lib/live.ts` (SSE with polling fallback). Settings validation and change summaries: `src/lib/settings.ts`. The Settings page is split into tabs (General, Battery, Schedule, System; `lib/settingsTabs.ts`, tab in the URL; the update badge opens System). Device status rules: `src/lib/devices.ts`. Runtime estimate and outage detection: `src/lib/runtime.ts`. Outage/alarm pairing and month/year energy sums: `shaping.pair_events` / `period_sums`. Views are URL-driven (`?view=devices&device=battery`). Translations: `src/lib/i18n.ts` (`t()` with the English text as the key, `tx()` to mark strings defined at module level, `tp()` for plurals, `unit()` for Вт/кВт·год/В/А/Гц) and `i18n.uk.ts`; every user-visible string must go through `t()` and have a Ukrainian entry (`i18n.test.ts` checks the keys found in the code, the placeholders, and the poller's fault names in `faults.py`). The four power gauges: `lib/gaugeRows.ts` builds each one's data (maximum, colour, note, loading/0 A states) and both `components/GaugeBars.tsx` draws the bars on both the Overview and the TV page. `useLang()` in `App` re-renders the tree on a language change. The Overview is two columns of cards chosen with **Customize** (`lib/layout.ts`: the card list, `defaultLayout`, pure move/add/drop rules; `components/OverviewEditor.tsx`: pointer-event drag with a drop line, arrow keys, the Add cards dialog; `components/MoreCards.tsx`: Power today, Self-sufficiency, Recent events, Battery health, Load by hour, each polling only while shown). The layout is kept by `web/backend/app/layout.py` (`LayoutStore`, `/data/overview-layout.json`, `LAYOUT_FILE`; `CARD_IDS` must match `lib/layout.ts`, `layout.test.ts` checks) via `routes/layout.py`: `GET /api/overview-layout` (open), `GET/POST /api/settings/overview-layout` (`WEB_BASIC_AUTH` + same-origin; null = the default). Until a layout is saved the default includes Planned outages only if its `show` setting is on; that setting otherwise only drives the TV page. `?view=tv` (`pages/Tv.tsx`, `lib/tv.ts`) is the wall display for the Android TV app: a fixed 1920×1080 stage scaled to the window, no nav, read-only. Its right column is gauges, `OutageStrip` (the compact planned-outage card, only when configured and `show`), the Power flows chart (`fill`: it takes the height left and redraws via its ResizeObserver, so it grows or shrinks with the strip) and Today.
- **`android/`**: Android TV app (Kotlin, no dependencies) that shows `http://<host>:<port>/?view=tv` in a WebView; `Config.kt` parses the configurable host/port (unit-tested). Built only through Docker (`sh android/build.sh`); it is not part of `docker-compose.yml` or the deploy, and never talks to the inverter or InfluxDB directly.

## Deployment

Every site, including the maintainer's (an Umbrel host and a second site on a Raspberry Pi reached over Tailscale, each with its own InfluxDB and `.env`), is a release install made with `install.sh` and updated only to tagged releases (`solis-monitor update`, or from the dashboard). Nothing deploys from `main` directly. `SITE_NAME` (poller + web) labels the site. To try unreleased work on one site, push a test tag (`v1.2.0-rc.1`, see below) and run `solis-monitor update --version v1.2.0-rc.1` there. A release can write inverter settings, so keep the test suites meaningful.

## Installer and releases (public install path)

- `install.sh` (repo root) is the one-command installer for Debian/Ubuntu/Raspberry Pi OS: prompts from `/dev/tty` (it runs piped from curl), scans the LAN for the Modbus logger, installs Docker, downloads `docker-compose.yml`, `.env.example` and `deploy/solis-monitor` from the release tag, pulls the prebuilt images, writes `/opt/solis-monitor/.env` with fresh secrets and `CONTROL_ENABLED=false`. It refuses to run over an existing install. `SOLIS_TEST_MODE=1`, `SOLIS_RAW_BASE`, `SOLIS_API_BASE`, `SOLIS_DIR` exist for the tests.
- `deploy/solis-monitor` is the management command installed next to it (`status`, `update`, `auto-update on|off`, `logs`, `secure-tokens`, `backup`, `restore`). `backup --from-dashboard` is what the host path unit runs for the Settings → Backup tab (request/status files like updates; a `set-folder` request is validated by `valid_backup_dir` — existing, writable, under an allowed root or `SOLIS_BACKUP_ROOTS` from `.env` — and kept in `control/backup-config.json`; after each backup `control/backups.json` indexes the folder for the page and only the newest `keep` dashboard-made archives stay; a `remove` request deletes one archive, by the strict name pattern, inside that folder only; a `restore` request (`restore_from_dashboard`) makes a safety backup unless `backup_first` is false, then runs `cmd_restore FILE --yes` with staged `breport`s — `cmd_restore`'s EXIT trap must keep `finish_breport`, or a failure mid-restore leaves the page waiting); `dashboard-updates on|off` installs or removes both path units. `backup` streams an online `influx backup` out of the container as a tar plus `/data` of poller and web, `.env` and the compose file into one private `.tar.gz`; `restore` does `influx restore --full` (so the restored `.env`'s tokens match the database), keeps only `SOLIS_IMAGE_PREFIX`/`SOLIS_VERSION`/`SOLIS_REPO` from the current `.env`, force-recreates the containers and puts the `/data` files back. `update` only moves to tagged GitHub releases, restores the old compose file and version if the new one is not healthy (both containers' own healthchecks), and never edits `.env` except `SOLIS_VERSION`. `secure-tokens` (run by `install.sh` once the database is up; older installs run it by hand) writes `CONTROL_TOKEN` and a read-only InfluxDB token as `INFLUX_READ_TOKEN`: the compose file gives the web container `${INFLUX_READ_TOKEN:-${INFLUX_TOKEN}}`, so the web service never needs the admin token and never writes to InfluxDB (keep it that way). The Umbrel app has `CONTROL_TOKEN` from `derive_entropy` but keeps the admin token for reading (nothing runs there after the database starts).
- `docker-compose.yml` has both `image:` and `build:` for poller and web: the image defaults to `solis-monitor-<service>:latest` (what a local build is called), the installer sets `SOLIS_IMAGE_PREFIX`/`SOLIS_VERSION` in `.env` to use the registry images.
- **Updating from the dashboard** (release installs only): `web/backend/app/updates.py` + `/api/settings/update*` in `routes/updates.py` + `UpdateCard.tsx`. The web container writes only `control/update-request`; a host systemd path unit (`solis-monitor dashboard-updates on`) runs `solis-monitor update --from-dashboard`, which finds the release itself, rolls back on failure and writes `control/update-status.json`. The server (not the browser) looks for a newer release every `UPDATE_CHECK_HOURS` and `/api/version` feeds the header badge (`UpdateBadge.tsx`), which opens Settings with the confirmation, never updating on a single click. Never give the web container Docker access or let the request choose what is installed.
- `.github/workflows/release.yml` builds amd64+arm64 images for a `v*` tag and creates the release with `install.sh` attached (its `DEFAULT_VERSION=` line is stamped with the tag). A suffixed tag (`v1.2.0-rc.1`) becomes a pre-release without the `latest` image tag, for testing on one site with `solis-monitor update --version`. Keep every new compose variable optional (`${VAR:-default}`): updates replace the compose file but not `.env`.
- `deploy/tests/test-install.sh` tests both scripts with a stand-in `docker`, a fake Modbus logger and `file://` releases; it runs in CI together with shellcheck.

## Umbrel community app store

This repository is also an Umbrel community store: `umbrel-app-store.yml` (id `vtlvolkov`) and `vtlvolkov-solis-monitor/` (manifest, compose, `exports.sh`, `hooks/pre-start`, `icon.svg`); user guide in `docs/umbrel.md`. The compose file there mirrors the main `docker-compose.yml` with Umbrel's rules: images pinned by digest, bind mounts under `${APP_DATA_DIR}/data`, no `container_name`/`build`/`ports`, `app_proxy` env, `restart: on-failure`. The owner's settings live in `data/config/settings.env`, read by `exports.sh`; secrets come from `derive_entropy`. The gallery images (`docs/img/store/`) must be exactly 1440×900 or umbrelOS crops and stretches them. `UPDATES_MANAGED_BY=umbrelOS` makes the dashboard show the version without any update machinery. **When you change the main compose** (a variable or mount for poller/web), change the Umbrel compose too: `deploy/tests/check-umbrel-app.py` fails otherwise. **After a release** the `umbrel-store` job of `release.yml` runs `deploy/umbrel/update-app.py vX.Y.Z` (the whole tag message, minus the `vX.Y.Z: ` prefix, becomes `releaseNotes`; everything after its first line also opens the GitHub release page above the generated commit list), the Umbrel checks, and pushes a commit to `main`, so umbrelOS offers the update. Suffixed test tags are skipped; a failure there leaves the release alone, then run the script by hand. The manual run (Actions → Run workflow, `store_tag`) is a dry run that pushes nothing.

## Changing things

- **New register**: add it to `REGISTERS` in `poller/poller.py` (registers are 0-based input-register addresses; `u32`/`s32` span two registers, high word first) **and** to `FIELDS` in `web/backend/app/validation.py`, or the API won't accept or return it.
- `INFLUX_RETENTION` and other `DOCKER_INFLUXDB_INIT_*` values only apply on the first start of a fresh volume.
